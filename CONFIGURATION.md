# Benchmark configuration

Every setting that affects the numbers is recorded here so the workload can be reproduced and
fairness checked.

This document describes the harness configuration, not the outcome of any particular round.
Round-specific results and observations belong in that round's report under [`reports/`](reports/).

Read [Known asymmetries](#known-asymmetries) for the known limits of the comparison.

How the measurements themselves are taken is in [`METHODOLOGY.md`](METHODOLOGY.md).


## The dataset

`buildDataset` in `shared/dataset.js` builds both shapes; each app maps its neutral output to
library-specific fields. Structure, ids, dates and edit targets therefore come from one source.

<!-- BENCH:DATASET -->

### The two dataset shapes

Every metric is measured on both, at every size and in both auto-scheduling modes. Both are generated by one function from one parameter, and both hold exactly as many records as the size says — so at a given size the two shapes put the same number of rows on screen.

**Flat chain.** One summary task holds every other task as a leaf directly under it, and each leaf is linked finish-to-start to the next, so the dataset is a single dependency chain running through all of it. With auto-scheduling on, moving one task reschedules every task after it, and every edit rolls up through a parent with as many children as the chart has rows. It is a stress test of both engines rather than a project shape anyone ships.

**Project tree.** A four-level project portfolio: the portfolio root, its projects, ten work packages per project and ten tasks per work package, which leaves about 90% of the records leaves at every size. Fanout inside a project is constant, so the shape stays the same from the smallest dataset to the largest and it is the number of projects that grows. Leaves are chained inside their work package and the last leaf of one package is linked to the first of the next in the same project, so no dependency crosses a project boundary and a cascade is bounded by one project. Every summary is loaded expanded, so the whole tree is on screen.

| Size    | Shape        | Summary rows | Leaves | Links  |
|---------|--------------|--------------|--------|--------|
| 1 000   | Flat chain   | 1            | 999    | 998    |
| 1 000   | Project tree | 100          | 900    | 891    |
| 5 000   | Flat chain   | 1            | 4 999  | 4 998  |
| 5 000   | Project tree | 498          | 4 502  | 4 456  |
| 10 000  | Flat chain   | 1            | 9 999  | 9 998  |
| 10 000  | Project tree | 993          | 9 007  | 8 916  |
| 50 000  | Flat chain   | 1            | 49 999 | 49 998 |
| 50 000  | Project tree | 4 957        | 45 043 | 44 592 |
| 100 000 | Flat chain   | 1            | 99 999 | 99 998 |
| 100 000 | Project tree | 9 911        | 90 089 | 89 188 |

Leaf count and link count differ between the shapes by about a tenth, which is the one quantity that cannot be held equal alongside equal record counts — so the two shapes are two workloads rather than one experiment with hierarchy as its variable, and a difference between a library's two rows is not attributable to hierarchy alone. Comparisons are between libraries within a shape.

### What is the same in both shapes

| Property | Value |
|---|---|
| Task count | 1 000 / 5 000 / 10 000 / 50 000 / 100 000, counting every record the store holds |
| Duration | 2 days, every leaf; a summary's dates are the span of everything beneath it |
| Start dates | spread across 2 years from 1 March 2026 (`DATASET_YEARS` in `bench/config.mjs`), keyed on a leaf's own position, so leaf 3 starts on the same day in both shapes |
| Progress | `(i % 10)`, expressed in each library's own scale (fraction or percent) |
| Dependencies | finish-to-start throughout, leaf to leaf |
| Expansion | every summary is loaded expanded, so all `size` records are on screen |
| Record ids | leaves are `1..n` in document order; summaries take a separate, non-colliding range |
| Milestones, constraints, calendars, resources | none |

The date spread matters: the visible window is three months wide (below), so most tasks sit
outside it and the chart has to handle them without rendering them.

Counting every record keeps row counts identical across libraries and shapes.

Expansion is mapped explicitly by every adapter: `open` in DHTMLX, `expanded` in Bryntum and
Kendo UI, `taskFields.expandState` in Syncfusion, and `expandAll()` in DevExtreme. This avoids
measuring a collapsed tree for one library.

### Why these two shapes

The flat chain is a stress workload. The project tree represents a portfolio and keeps constant
fanout as size grows. Both come from the same generator and size parameter.

Both shapes carry summary rows through each library's native mechanism (`type: "project"` in
DHTMLX, parent tasks in Bryntum, `summary: true` in Kendo UI, `autoUpdateParentTasks` in
DevExtreme and automatic parents in Syncfusion). Summary dates roll up from children and are
part of edits; omitting parents would not exercise equivalent hierarchy handling.


## Common conditions

| Condition | Setting |
|---|---|
| Visible time window | 1 March 2026 – 1 June 2026 |
| Timeline tiers | week over **day** in every app — roughly 92 day columns across the window |
| Row height | **36 px** in every app (`ROW_HEIGHT` in `shared/layout.js`) |
| Grid width | **380 px** in every app (`GRID_WIDTH` in `shared/layout.js`), leaving ~1 220 px of timeline |
| Grid columns | two — task name and progress |
| Selection | enabled |
| Editing | enabled |
| Parent tasks | expanded, and rolled up from their children in every app |
| Row virtualization | on in every library that has it; Kendo UI exposes no equivalent option — see [Known asymmetries](#known-asymmetries) |
| Viewport | 1600 × 900, fixed for every cell |
| Starting scroll position | top of the task list, left edge of the timeline |
| Auto-scheduling | measured twice, once off and once on |
| Dataset shape | measured twice, once flat and once tree |

Anything not listed remains at the library's default; hand-tuning would measure the tuner.

Timeline granularity, row height and grid width are pinned in `shared/layout.js` because they
control rendering inside the fixed viewport. Kendo UI additionally needs `showWorkDays: false`
to retain weekend columns; see its section below.

Row and timeline virtualization is enabled wherever available. DHTMLX, Bryntum and DevExtreme
already enable row virtualization; Syncfusion's two virtualization options are explicit. Kendo
UI exposes no equivalent option; see [Known asymmetries](#known-asymmetries).

Grid width is pinned because defaults differ: at this viewport DHTMLX was about 319 px and Kendo
UI 475 px (`listWidth: "30%"`), versus 380 px in the other three. The common 380 px avoids a
timeline-width confounder.


## Per-library configuration

Each app's `src/components/GanttChart.js` is the authority. Reproduced here so you do not
have to clone the repository to audit it. Which apps exist, on which ports and from which
packages, is in [`apps.json`](apps.json); which of them a round measures is in
[`round-apps.json`](round-apps.json).

### DHTMLX Gantt

```js
gantt.plugins({ auto_scheduling: true });
gantt.config.grid_width = 380;
gantt.config.columns = [
  { name: "text", label: "Name", tree: true, width: 280 },
  { name: "progress", label: "Progress", width: 100,
    template: (obj) => `${obj.progress * 100}%` },
];
gantt.config.start_date = new Date(2026, 2, 1);
gantt.config.end_date = new Date(2026, 5, 1);
gantt.config.show_tasks_outside_timescale = true;
gantt.config.scales = [
  { unit: "week", step: 1, format: "%d %M" },
  { unit: "day", step: 1, format: "%d" },
];
gantt.config.row_height = 36;
gantt.config.auto_scheduling = { enabled: <mode> };
```

The scales are DHTMLX's default granularity. Bar height and smart rendering remain at their
defaults. Its columns sum to the pinned 380 px, which is also set as `grid_width`.

### Bryntum Gantt

```js
new ProjectModel({ autoSetConstraints: true, tasks: [], dependencies: [] });

new Gantt({
  project,
  startDate: new Date(2026, 2, 1),
  endDate: new Date(2026, 5, 1),
  viewPreset: "weekAndDay",
  rowHeight: 36,
  barMargin: 6,
  subGridConfigs: { locked: { width: 380 } },
  columns: [
    { type: "name", text: "Task name", width: 260 },
    { text: "Progress", field: "percentDone", width: 100, editor: false,
      renderer: ({ value }) => `${Math.round(value || 0)}%` },
  ],
});
```

`weekAndDay` supplies the week-over-day tiers. Auto-scheduling is per task, so the mode sets
`manuallyScheduled = !enabled` on every leaf and commits once.

### DevExtreme Gantt

```js
$(el).dxGantt({
  startDateRange: new Date(2026, 2, 1),
  endDateRange: new Date(2026, 5, 1),
  scaleType: "days",
  taskListWidth: 380,
  rootValue: 0,
  height: "calc(100vh - 60px)",
  validation: {
    validateDependencies: <mode>,
    autoUpdateParentTasks: true,
    enablePredecessorGap: <mode>,
  },
  editing: { enabled: true },
  columns: [
    { dataField: "title", caption: "Task name", width: 260 },
    { dataField: "progress", caption: "Progress", width: 100 },
  ],
});
```

`validateDependencies` is DevExtreme's edit-time auto-scheduling switch: predecessor validation
pushes successors after a change, rather than scheduling on load. All links are finish-to-start;
the benchmark edits avoid validation dialogs. `enablePredecessorGap` follows the mode and snaps
an early successor to its predecessor's new end.

`autoUpdateParentTasks` is enabled so DevExtreme performs the parent rollup inherent in the
other four libraries.

DevExtreme has no `rowHeight` option, so 36 px is applied as CSS to task-list rows and
propagates to the timeline. After loading, the app calls `scrollToDate(new Date(2026, 2, 1))`
because its default view is near the empty right edge of the timeline.

### Kendo UI Gantt

```js
$(el).kendoGantt({
  height: "100%",
  dataSource: new kendo.data.GanttDataSource({ autoSync: false, data: [] }),
  dependencies: new kendo.data.GanttDependencyDataSource({ autoSync: false, data: [] }),
  editable: true,
  navigatable: true,
  rowHeight: 36,
  listWidth: "380px",     // its default is 30%, i.e. 475 px at this viewport
  showWorkDays: false,    // render all seven days, like the other four apps
  views: [{ type: "week", selected: true }],
  range: { start: new Date(2026, 2, 1), end: new Date(2026, 5, 1) },
  columns: ["title", "percentComplete"],
});
```

`views: [{ type: "week" }]` is Kendo UI's week-over-day view. Its `day` view shows hour slots
inside one day and is not the required three-month day timeline.

Kendo UI hides weekends by default, yielding 65 rather than 92 day columns and changing bar
widths. `showWorkDays: false` restores all seven days to match the other apps; `showWorkHours`
does not affect a week-over-day view.

Kendo UI's `percentComplete` prints the stored fraction (`0.1`) rather than the formatted
`10%` used elsewhere; the field and column count are unchanged.

`rowHeight` is a floor in the default theme. Values below 36 px create a mismatch between
dependency-line geometry and rendered table rows, so 36 px is the smallest common exact value.

**Kendo UI Gantt renders every row: this build exposes no row-virtualization option.** Its
TreeList virtual-scroll setting cannot be reached through Gantt. The DOM difference is quantified
in [Known asymmetries](#known-asymmetries).

Kendo UI Gantt has no auto-scheduling feature, so enabled cells are not applicable rather than
copied from disabled cells. See Telerik's [forum thread](https://www.telerik.com/forums/gantt-chart--calculate-dates-for-dependant-tasks)
and [API reference](https://docs.telerik.com/kendo-ui/api/javascript/ui/gantt).

### Syncfusion Gantt

```js
new Gantt({
  height: "calc(100vh - 60px)",
  treeColumnIndex: 0,
  rowHeight: 36,
  taskbarHeight: 22,
  highlightWeekends: true,
  allowSelection: true,
  enableVirtualization: true,
  enableTimelineVirtualization: true,
  enablePredecessorValidation: <mode>,
  validateManualTasksOnLinking: true,
  taskMode: "Custom",
  splitterSettings: { columnIndex: 1, position: "380px" },
  timelineSettings: {
    timelineUnitSize: 72,
    topTier: { unit: "Week", format: "dd MMM yyyy" },
    bottomTier: { unit: "Day", format: "dd" },
  },
  editSettings: { allowAdding: true, allowEditing: true, allowDeleting: true,
                  allowTaskbarEditing: true, mode: "Auto" },
  columns: [
    { field: "name", headerText: "Task name", width: 260 },
    { field: "progress", headerText: "Progress", width: 100,
      template: ({ progress }) => `${Math.round(progress || 0)}%` },
    { field: "id", headerText: "ID", isPrimaryKey: true, visible: false },
  ],
  projectStartDate: new Date(2026, 2, 1),
  projectEndDate: new Date(2026, 5, 1),
});
```

`Gantt.Inject(DayMarkers, Edit, Selection, VirtualScroll)`. `enablePredecessorValidation` is
Syncfusion's auto-scheduling switch.

The hidden `id` column is required: without `isPrimaryKey`, TreeGrid logs "PRIMARY KEY MISSING"
and `updateRecordByID` throws. It is last and hidden, so the visible columns and layout remain
task name plus progress.


## How auto-scheduling is expressed

The libraries model this differently, which is worth stating plainly, because
"auto-scheduling on" is not one setting:

| Library | Switch | Scope |
|---|---|---|
| DHTMLX | `config.auto_scheduling.enabled` | whole chart |
| Bryntum | `task.manuallyScheduled = !enabled` on every leaf, then `commitAsync()` | per task |
| DevExtreme | `validation.validateDependencies` (+ `enablePredecessorGap`) | whole chart |
| Kendo UI | — | feature absent |
| Syncfusion | `enablePredecessorValidation` + `manual` flag per task | both |

Bryntum and Syncfusion apply the mode per task, so it is set **before** loading; mode-switch cost
is excluded from every metric.

For DHTMLX, programmatic `updateTask()` leaves scheduling to the caller. Both edit tests call
`gantt.autoSchedule()` inside the timed step: scoped to the moved task, or once over the chart
at the end of the bulk batch.


## Editions and delivery

**Each component uses the latest stable build publicly obtainable on the round's cutoff date; no
version changes after measurement starts.** Related theme and engine packages use that build.

| Library | Version | Package | Registry |
|---|---|---|---|
| DHTMLX Gantt | 10.0.3 | `@dhx/trial-gantt` | `npm.dhtmlx.com` |
| Bryntum Gantt | 7.3.6 | `@bryntum/gantt-trial` | npm |
| DevExtreme Gantt | 26.1.4 | `devextreme` + `devexpress-gantt` 4.1.70 | npm |
| Kendo UI Gantt | 2026.3.811 | `@progress/kendo-ui` + `@progress/kendo-theme-default` 14.5.0 | npm |
| Syncfusion Gantt | 34.2.8 | `@syncfusion/ej2-gantt` + `@syncfusion/ej2` (theme) | npm |

All components, themes and required jQuery (4.0.0) are exact install-time dependencies. No
library build is vendored; `npm ci` with the committed lockfiles installs the measured code. The
DHTMLX registry is anonymously readable via the committed `.npmrc` mapping.

**No internet requests occur during measurement.** The browser blocks requests outside the local
preview server, including Google webfonts, so all apps use their stylesheet's fallback font.

Versions in the published tables are read from the installed packages at run time rather than
typed into this document.

**Trial builds are used without licence keys.** Watermarks and licence banners are part of the
measured page; licensed builds require a fresh measurement.


## Measurement settings

What each of these means is in [`METHODOLOGY.md`](METHODOLOGY.md); the values are:

| Setting | Value |
|---|---|
| Browser | pinned Playwright Chromium, headed |
| Chrome flags | `--enable-precise-memory-info`, background throttling disabled |
| Runs per cell | 3 independent fresh-browser runs; each metric's **median** is taken from the runs that produced a figure for it, and a figure measured by fewer carries that count |
| Practical equivalence | measurements within 25% (`larger / smaller <= 1.25`) are treated as comparable |
| DNF threshold | 300 s per timed step |
| Settle cap | 300 s from the start of the operation; a step that reaches it is reported as *did not settle*, never as a number |
| Bulk-edit batch | 100 updates + 100 deletions + 100 insertions, the updates applied last record first; an update extends a record's end by one leaf duration |
| Timing endpoint | quiescence — five consecutive frames under 32 ms, reported at the last busy frame |
| First-paint endpoint | the first frame with rows on screen, in the same load |
| Memory sampling | after a `HeapProfiler.collectGarbage` over the DevTools protocol; if that call fails the runner logs it and samples anyway |
| Display refresh | measured per machine at startup, recorded in the environment block, and used to validate the FPS column |

## Known asymmetries

These are the known places where the libraries are not asked for exactly the same thing; publish
them with any conclusions drawn from the numbers.

**1. Bulk editing spans three orders of magnitude.** All libraries edit in place, but only DHTMLX
and Bryntum suspend rendering across the batch; the other three repaint per change. Mechanisms are
documented in [`METHODOLOGY.md`](METHODOLOGY.md#what-each-metric-measures).

**2. The two shapes have different leaf and link counts.** Both hold `size` records, preserving
row counts, while the project tree spends about a tenth of records on summaries. They are separate
workloads, not a controlled hierarchy comparison; compare libraries within one shape.

**3. Every library but Kendo UI virtualizes rows.** Kendo UI exposes no option. At 1,000 flat
records in this viewport, task-list rows are:

| Library | Rows in the DOM |
|---|---|
| DHTMLX | 23 |
| DevExtreme | 25 |
| Bryntum | 32 |
| Syncfusion | 45 |
| Kendo UI | 1 000 — every row |

The timeline pane holds 23, 33, 32 and 45 bars for the first four; Kendo holds 208 bars inside
the visible time range. This capability difference is not compensated for in the measurements.

**4. Benchmark-selected settings differ from library defaults.** Common layout conditions such as
the viewport, grid width, row height, visible dates and timeline tiers are listed above. The
additional non-default choices are:

| Library | Setting | Library default | Benchmark value | Reason and effect |
|---|---|---|---|---|
| DHTMLX | `show_tasks_outside_timescale` | `false` | `true` | Draws clamped bars for tasks outside the visible range. The other components omit those bars, so this adds work for DHTMLX rather than benefiting it. |
| Bryntum | `autoSetConstraints` | `false` | `true` | Preserves the generated spread of start dates instead of rescheduling tasks to the project start. It creates a constraint per task and can increase retained memory. |
| Bryntum | `barMargin` | preset/theme-derived | `6` | Keeps the task bars at the intended height inside the common 36 px rows; cosmetic. |
| DevExtreme | `validation.autoUpdateParentTasks` | `false` | `true` | Enables parent rollup so DevExtreme performs the summary-date work inherent in the other four components. |
| Kendo UI | `showWorkDays` | `true` | `false` | Restores weekend columns, increasing the window from about 65 to 92 day cells and matching the other components. |
| Syncfusion | `highlightWeekends` | `false` | `true` | Paints weekend highlighting across the visible timeline; this adds work for Syncfusion. |
| Syncfusion | `enableVirtualization` | `false` | `true` | Enables row virtualization, matching the other components that provide it. |
| Syncfusion | `enableTimelineVirtualization` | `false` | `true` | Enables timeline virtualization, matching the other components that provide it. |
| Syncfusion | `timelineSettings.timelineUnitSize` | `33` | `72` | Brings its day columns close to DHTMLX's 70 px default; see asymmetry 8. |
| Syncfusion | `validateManualTasksOnLinking` | `false` | `true` | Applies predecessor validation to manual tasks, including leaves in the auto-scheduling-off workload. |
| Syncfusion | `taskMode` | `"Auto"` | `"Custom"` | Allows the shared per-task `manual` field to express both auto-scheduling modes. |
| Syncfusion | `taskbarHeight` | derived from the row/theme | `22` | Keeps the task bars at the intended height inside the common 36 px rows; cosmetic. |

The common 380 px grid width gives DHTMLX about 60 px less timeline and Kendo UI about 95 px more
than their defaults.

**5. DevExtreme schedules on change, not load.** Its auto-scheduling-on load figures are not
directly equivalent to libraries that schedule while ingesting; move figures are comparable.

**6. DevExtreme expands in a second pass.** Its adapter calls `expandAll()` inside the timed
region after assigning data; the other libraries carry expansion on each record.

**7. Trial builds include watermarks or licence banners.** These differ by library and remain
in the measured page for reproducibility.

**8. Day-column widths are close but not identical.** Measured in the rendered day-tier headers at
1 000 records and the fixed 1600 × 900 viewport:

| Library | Rendered day width | How it is determined |
|---|---:|---|
| DHTMLX | 70 px | Library default; `min_column_width` is not overridden. |
| Bryntum | 100 px | Set by the benchmark-selected `weekAndDay` preset. |
| DevExtreme | 112 px | Produced by the `days` scale; DevExtreme exposes no day-width setting. |
| Kendo UI | 100 px | Produced by Kendo UI's week-over-day view; the benchmark does not override it. |
| Syncfusion | 72 px | Pinned by the benchmark with `timelineUnitSize: 72`. |

Syncfusion's width is therefore a controlled benchmark choice, while DevExtreme's is an
uncontrolled consequence of the only scale that provides the required day granularity.
